# Chutes — Shared Platform Facts

Facts common to both Chutes surfaces (consumer inference, provider rental). The two
reports — [`REPORT-inference.md`](./REPORT-inference.md) and
[`REPORT-rental.md`](./REPORT-rental.md) — assume everything here and do not restate it.

**Target:** `chutes.ai` — serverless AI on Bittensor **subnet 64** (Rayon Labs / chutesai).
Confidential (`-TEE`) workloads on Intel TDX + NVIDIA confidential-compute GPUs, ML-KEM-768 E2E.
First **Bittensor-subnet** case and first **non-dstack custom TDX stack** in this cohort: its own
attestation sidecar, measurement registry, and LUKS key release.

**Audit dates:** source pass 2026-05-25 · guest-build (`sek8s`) pass 2026-05-25 · live operator PoC 2026-06-16/17
**Repos (HEAD at clone; org renamed `rayonlabs → chutesai`, 301 redirect):**
`chutes` `08d79872` (SDK) · `chutes-api` `77b6f355` (control plane) · `chutes-miner` `7afea4b1` (operator) · `sek8s` (guest TDX VM build, MIT)
**Live at probe:** 13 models on `llm.chutes.ai`, 12 `confidential_compute: true`; 10 published measurement configs across h200 / b200 / RTX PRO 6000.

Two verification regimes coexist; only the second is confidential and in scope:
**GraVal** (GPU proof-of-possession, no confidentiality) for normal chutes, and the **TDX flow**
(Intel TDX CVM + NVIDIA CC mode + ML-KEM-768 E2E) for the `-TEE` chutes.

## Trust topology (TEE path)

```
client ──── ML-KEM-768 E2E (prompt ciphertext) ─────────────────────────┐
   │  also fetches + (should) verify the quote                          │
   ▼                                                                     ▼
chutes-api control plane  ── picks instance, hands out e2e_pubkey+nonces, relays, bills
   │  sees: routing, user↔chute↔instance, timing, token COUNTS. (Ciphertext only on the E2E path.)
   ▼  (adds a transport-encryption layer around the still-E2E-encrypted blob)
miner host (permissionless, OUTSIDE the trust boundary)
   │  k8s Job; rootfs LUKS key released post-boot-attestation
   ▼
┌─ Intel TDX CVM (sek8s base image) ──────────┐   ┌─ 8× NVIDIA GPU (CC mode) ─┐
│ aegis lib holds ML-KEM privkey (in-TD)       │   │ per-GPU NRAS evidence,    │
│ vLLM/SGLang + model weights (pulled at boot) │   │ nonce-bound to the TD     │
│ + operator-authored serve.py (UNMEASURED)    │   └───────────────────────────┘
└──────────────────────────────────────────────┘
        ▲ report_data[0:32]=SHA256(nonce‖e2e_pubkey)   report_data[32:64]=SHA256(attest-svc cert SPKI)
```

## 1. The cryptographic core is sound (verified live)

A client who does the work can prove it is talking to a real, non-debug Intel TDX enclave whose
ML-KEM-768 key is hardware-bound, with per-request freshness, and that the control plane and miner
host see only ciphertext **on the E2E path**. Confirmed against the live API (`verify/verify_chutes.py`,
~5s):

```
[1] report_data[0:32] == SHA256(nonce+pub)  : True   (E2E key hardware-bound)
[2] two nonces -> different report_data      : True   (per-request freshness — quote regenerated in-TD)
[3] debug mode disabled                      : True   (td_attributes bit 0 = 0)
[4] report_data[32:64] == SHA256(cert SPKI)  : True   (attestation-service TLS cert bound into quote)
[5] MRTD in published golden set             : True
```

- **Authoritative binding:** `instance/util.py:1073` — `hashlib.sha256((nonce + e2e_pubkey).encode())`.
  Byte-for-byte the formula in our [redpill case study](../redpill-federated-inference/DEVPROOF-REPORT.md)'s
  `chutes.ts`; Redpill federates to these backends.
- **ML-KEM private key stays in-TD:** generated by the native `aegis` library, never leaves
  (`chutes/entrypoint/run.py:789-801`). `/e2e/invoke` only wraps/relays ciphertext and reads plaintext
  token *counts* for billing (`e2e/router.py:243,251,380-418`).
- **Client flow (third-party path), all confirmed live:**
  1. `GET /e2e/instances/{chute_id}` → `{instances:[{instance_id, e2e_pubkey, nonces[]}]}`. `nonces[]` are single-use **relay** tokens, *not* the attestation binding.
  2. `GET /instances/{instance_id}/evidence?nonce=<64 hex>` → `{quote, gpu_evidence[], certificate}`; client supplies the nonce, the instance regenerates a TDX quote bound to it (`server/service.py:1098-1137`).
  3. Verify: DCAP signature, debug off, `report_data[0:32]==SHA256(nonce‖e2e_pubkey)`, MRTD/RTMRs vs golden, GPU evidence via NRAS.
  4. `POST /e2e/invoke` relays the ML-KEM-encrypted blob.
- **Cert binding caveat (informational):** `report_data[32:64] == SHA256(SPKI)` of the returned
  `certificate`, whose subject is `CN=attestation-service` (host's internal proxy at `10.43.50.50:8443`,
  `chutes/constants.py:4`). This binds the attestation-service endpoint, **not** the E2E channel —
  E2E integrity rests entirely on `report_data[0:32]`. `/instances/{id}/evidence` does no server-side
  verification; it proxies raw quote+cert (`server/service.py:1098-1114`). All checking is the client's job.

## 2. Base-image provenance is reachable (not TOFU)

The TDX guest VM (TDVF/OVMF, kernel, initrd, rootfs) is published in **`chutesai/sek8s`** (MIT):

- `guest-tools/` + `ansible/guest/` build the encrypted TDX VM (k3s + attestation service + GPU drivers).
- Committed boot inputs: `firmware/TDVF.fd`, `metadata.json` (TDVF + `vmlinuz`/`initrd` + fixed cmdline & root UUID).
- `guest-tools/scripts/{extract-vm-measurements,extract-acpi,compute-measurements}.sh` recompute MRTD + RTMR0–2 with Intel `tdx-measure`; `compute-rtmr3.sh` recomputes the RTMR3 file-manifest.
- Prebuilt image at `https://vm.chutes.ai/tdx-guest.qcow2` (public, no auth) with a git-committed SHA-256 `1d53800f1c18e353ce43bbad886f3b38555b7fc38c3362b04af30d11a16f7b46` (`host-tools/scripts/quick-launch.sh:17-20`).
- Live quotes match the published `/servers/tee/measurements` golden set exactly (one MRTD `DDC6EFCD…EC38C` across all hardware classes).

So a third party can download the exact base image, verify the hash, audit the boot chain + admission
policy from source, and recompute the golden MRTD/RTMR0–2. This **supersedes** the original report's "golden
values are TOFU" framing. Residual gaps (the open items below): bit-for-bit rebuild from Ansible source is
unproven; the qcow2 is anchored only by a maintainer-committed git hash (no detached signature, no SLSA
build provenance — `.github/workflows` has CI/lint but no `attest-build-provenance`); `cosign.pub` is
baked into the LUKS rootfs and unpublished.

**Rekor transparency lever (R5):** `forge` signs chute images with cosign v2 (`2.6.3`) using `--key` and
**no** `--tlog-upload=false` → key-signed entries land in the public Rekor tlog by default; the admission
policy also pins `rekor_url`, so tlog inclusion is effectively required to schedule. Every chute image Chutes
signs should produce a public, timestamped Rekor entry — an auditor can enumerate Chutes' signing history
without the private registry. Querying by key needs the unpublished `cosign.pub`; querying by digest works.

## 3. The miner is contained (a malicious host cannot swap code or read memory)

The permissionless miner is outside the trust boundary, and three measured mechanisms keep it there:

1. **Measured, fail-closed admission control.** Chute workloads run under k3s with an OPA+cosign
   ValidatingAdmissionPolicy in `enforce` mode, `failurePolicy: Fail` (`manifests/webhook-vap.yaml:7`,
   `validating-webhook.yaml.j2:21`), default-deny on a catch-all `"*"` registry entry (unsigned images
   don't schedule). It is self-protecting (`webhook.rego` denies creating/modifying webhooks) and gated on
   integrity (`generate-admission-cert.service` `Requires=rtmr3-verify.service`). It runs *inside* the
   attested guest, so its code is auditable from `sek8s`.
2. **TEE-gated LUKS key release.** The rootfs is dm-crypt LUKS2 (no dm-verity), but the key is released
   **only into measured-guest TEE memory**: `fetch_key_and_unlock` generates a TDX quote *inside the TD*
   (`tdx-quote-generator`), binds an ephemeral cert into `report_data`, and the control plane returns the
   key over mTLS **only if the quote matches golden measurements**. A modified initramfs changes RTMR1 →
   key withheld. The host can't read TEE memory, so a miner cannot extract the key to tamper the rootfs offline.
3. **RTMR3 policy measurement (v1.3.0+).** `tdx-measure.conf` extends `/etc/opa/policies`, `/opt/sek8s/src`,
   the admission CA, and SSH/sudoers/PAM into RTMR3 (SHA-384 chain in initramfs). Tampering becomes
   tamper-evident in the quote. (Pre-v1.3.0 golden configs show RTMR3 = 0.)

**Consequence:** the original report's "a compromised *miner* can swap the model" is **refuted**. The
threats that remain are *trusting Chutes' control plane* (consumer report) and *trusting Chutes' server-side
build + signing key* (rental report) — not the host.

## 4. The root gap that splits the two reports

**The chute's application code (`serve.py`/cords) and model weights are in no measured register.** RTMR3
tracks only the fixed `sek8s` base-VM files (and reads 0 in production pre-v1.3.0); `model_name`/`revision`
are never extended into any RTMR nor placed in `report_data`. Weights are pulled at container start
(`chutes/chute/template/vllm.py:335-337`), vLLM launched `--model … --revision …` (`vllm.py:466-471`), and
the two mechanisms that could catch a swap are disabled on the TEE path: the launch-time command check
(`verify_expected_command`) is only called from the GraVal path (`instance/router.py:1719` vs the TEE
validator at `:1728`), and the weight-digest monitor explicitly excludes TEE (`watchtower.py:91`,
`env_type != "tee"  # Exclude TEE`).

A verified quote therefore proves "genuine TDX+GPU running *a* Chutes-blessed base image," not "*this* model
on *this* code." The same fact is a **confidentiality + identity** gap for a consumer
([`REPORT-inference.md`](./REPORT-inference.md)) and a **provability** gap for a provider
([`REPORT-rental.md`](./REPORT-rental.md)).

**Fix (shared):** extend `SHA256(image_digest ‖ model ‖ revision ‖ serve.py)` into RTMR3 and publish
model-keyed golden values; disclose the registered chute `code` (currently `code: null` even on public
`-TEE` chutes) so the measured value has a readable preimage.

## 5. Lower-tier shared facts (operator-trust / enforced server-side)

- **Static fleet-wide LUKS key (F5).** Boot attestation returns `get_luks_passphrase()` =
  `settings.luks_passphrase`, one static `LUKS_PASSPHRASE` identical for every node
  (`server/util.py:364-377`, `config/__init__.py:415`, returned at `server/router.py:127`). Release is
  measurement-gated and the key is **never host-extractable** (§3.2), and it encrypts a *public* image, so
  its confidentiality value is low. Residual: Chutes can decrypt any node's rootfs; fleet-wide blast radius
  if the control-plane key leaks. Per-volume cache passphrases ≥v1.3.0 are already random + Fernet-encrypted
  per node (`server/util.py:535-577`). **Operator-trust, Low.**
- **GPU verdict only via NVIDIA NRAS (F4).** Each GPU's raw evidence embeds `SHA256(nonce‖e2e_pubkey)`
  (proving the GPUs and the TD are one machine — verified live), but genuineness / CC-mode / RIM matching
  come from NVIDIA's hosted NRAS (`server/util.py:623-645` → `Environment.REMOTE`,
  `nv-attest/.../verifier.py:6-13`). The validator enforces NRAS CC-mode at TEE registration
  (`instance/util.py:1077`), so an instance failing CC-mode never gets traffic. The only gap is that a
  *client* can't re-verify offline without calling NVIDIA. **Enforced server-side, Low.**
  Fix: offer NVIDIA's `LOCAL` GPU verifier (bundled RIM) for self-contained client checks.
