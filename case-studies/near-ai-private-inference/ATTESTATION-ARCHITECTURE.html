NEAR AI — Attestation Architecture & Trust Chain

How a verifying client connects hardware reference values to the public key it encrypts its prompt to. Values are from a live capture (openai/gpt-oss-120b, 2026-05-05).

1 · The one idea: two channels, one binding

The prompt is encrypted to the model enclave's key — not to the TLS endpoint. TLS is transport; the privacy boundary is the model CVM's public key. The gateway only forwards ciphertext it cannot read.

The CPU TD and the GPUs are separate hardware with separate attestations. The decrypted prompt only crosses between them over the encrypted CC session, and a CC-On GPU accepts work from this one TD only — that link is the whole integrity question (§6).

Attestation path — the nonce N is baked into both attestations, not just held by the client

The client mints one fresh N and sends it with the report request. Each trust domain stamps N into its own hardware attestation:

CPU TD →
TDX quote · report_data = [ signing addr │ N ]
▶ Intel DCAP
8× H100 →
GPU evidence · eat_nonce = N  (device-key signed)
▶ NVIDIA NRAS

Both return to the client in one report; the client confirms N appears in both. So N lives in three places — client, TDX quote, GPU evidence — and is the thread joining the two domains. What it does not do: tie the GPU's session to this TD (§6).

Outer channel (attested TLS) proves which gateway you reached. Inner channel (E2EE) is what keeps the prompt private — a fully malicious gateway with no TEE still cannot read prompts.

3 · The nonce-pairing system

The client mints one fresh N (32 random bytes). The enclave produces two attestations, both keyed to that same N:

TDX quote — report_data (64 bytes)

Model CVM quote:

[0:32]   signing_address (20B) ‖ 00…00
[32:64]   nonce N

Gateway quote (TLS-fingerprint mode):

[0:32]   SHA256( signing_address ‖ tls_cert_fingerprint )
[32:64]   nonce N

Code identity: mr_config = 01 ‖ SHA256(app_compose) — the running docker-compose is committed in the quote.

GPU evidence — NVIDIA

Collected with cc_admin.collect_gpu_evidence_remote(N). N goes into the SPDM measurement request and the GPU device key signs the report over it. NRAS echoes it back as eat_nonce. The GPU evidence commits to N only — the signing key is not in it.

The two threads to draw:

  • N is the horizontal thread joining the TDX box and the NRAS box (report_data[32:64] == eat_nonce == N).
  • report_data[0:32] is the vertical thread pinning the TDX box down to the E2E key the client encrypts to.
  • The GPU box connects only on the N thread — draw it dashed (see §6).

4 · Trust chain — connecting reference values to the key

This is the verify-then-encrypt sequence. Each step rejects on failure; only after all pass does the client encrypt.

  1. Request. GET /v1/attestation/report?model=M&nonce=N&signing_algo=ecdsa&include_tls_fingerprint=true
  2. Verify the model TDX quote with dcap-qvl → genuine Intel TD, TCB acceptable. Extract report_data and mr_config.
  3. Freshness: report_data[32:64] == N → this quote answers this challenge (not a replay).
  4. Key binding: report_data[0:32] == signing_address → the freshly-attested TD vouches for this exact address.
  5. Key derivation: keccak256(signing_public_key[1:])[-20:] == signing_address → the public key on offer is the one the hardware bound (ECDSA path; for Ed25519 the address is the key).
  6. Code identity: mr_config == 01 ‖ SHA256(app_compose), and app_compose is in the pinned allow-set (on-chain anchors / compose_hashes) → the right image is running, not just a TD.
  7. GPU: POST the GPU evidence to NRAS → overall-att-result == True and eat_nonce == N → genuine, fresh H100s in the same round.
  8. Encrypt. Only now: encrypt the prompt to signing_public_key. The private half derives only inside the model TD, so only that enclave can decrypt. ECIES (secp256k1) or X25519+ChaCha20-Poly1305 (Ed25519).

Steps 3–5 are the load-bearing join: fresh quote → this address → this public key. Step 6 says the quote came from the audited code; step 7 says a real GPU is present in the same round. The key the client trusts in step 8 is therefore tied, by reference values, all the way back to genuine hardware running known code.

Every NRAS claim is about the GPU's own firmware (driver + VBIOS, against NVIDIA-signed golden RIMs) — none measure the model weights, kernels, or container code. That binding lives entirely on the TDX / mr_config side.

6 · What's load-bearing — and what it rests on

What stops a foreign CPU from swapping weights or injecting a kernel: CC-On, not the nonce. A CC-On H100 binds to exactly one CPU TD via an SPDM session; its firewalls block every other CPU/host from the protected memory (CPR), and all kernel launches + DMA go over an AES-GCM-256 channel keyed to that session. So a different CPU has no session keys — it cannot submit a kernel, read activations, or overwrite weights. That tampering is only possible if the GPU is CC-Off (an ordinary GPU any host can drive). Integrity therefore rests on two things: (a) the GPU is CC-On, and (b) its session is bound to the attested TD.
Both (a) and (b) are established — by pinning the code, not by a GPU claim. A CC-Off GPU cannot produce a valid CC attestation at all, so a mandatory, enforced NRAS PASS rules out CC-Off by construction (this is why GPU attestation must be hard-required, not soft-failed). CC-On and the TD-binding are then carried by the measured, pinned code: the audited inference-proxy collects evidence from — and runs inference on — its own GPUs. So pinning compose_hash (Block B/C, which hermes does) makes the GPU↔TD binding sound by construction — the code that computes is the code that verified. The bare-nonce weld and the absence of a CC-mode claim don't open an attack for a pinning client; they would only matter if you ran unpinned code or soft-failed NRAS.
Checked and ruled out (software-adversary model; physical attacks out of scope, as for the TDX die itself):
  • CC-DevTools (would re-open side channels) — not engaged: live attestation shows dbgstat=disabled, secboot=True → CC-On.
  • Decoy GPU (attest one card, compute on another) — foreclosed by compose pinning: collecting evidence from elsewhere requires modified code, which changes compose_hash.
  • Multi-GPU NVLink (H100 CC doesn't encrypt GPU↔GPU NVLink; NEAR runs TP=4–8 for DeepSeek / GLM / Qwen) — cross-GPU activations travel GPU-to-GPU on NVLink, or PCIe-through-CPU via encrypted bounce buffers; never host-mappable, so only a physical NVLink/NVSwitch tap reads them → out of scope.
